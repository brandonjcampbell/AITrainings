Trust nothing you haven't tested

Proving Grounds

No camp sends a new radio out on patrol because it worked once in the tent. It goes to the proving grounds first, against the same course every time. LLM apps need the same discipline. An eval is a fixed set of test cases, graders that score each output, and a number you can compare across versions. It's how you know whether a change made things better or worse instead of guessing from a few chats.

Who it's for

Engineers shipping LLM features, and product owners who decide when a change is ready.

Time

About 75 minutes. Parts 1 to 5 need no code.

Bring

An LLM feature you care about. For Part 6: Python 3.10+, pip install ollama pydantic, and a pulled model (Field Manual 4).

  • Same course, every time.

    Compare versions on the same fixed cases. A score only means something next to another score from the same set.

  • Pick the cheapest grader that works.

    Code checks first. A model as judge only where code can't decide, and only after you've checked it against people.

  • Small sets have wide error bars.

    With 20 cases you can't tell 80% from 85%. Report intervals, and compare variants case by case.

Part 1 · Why the tent test fails

Vibes are not evidence

The usual test goes like this: change the prompt, try three questions, like what you see, ship. It fails for three reasons that compound.

The dice roll

The model samples each token, so the same prompt can give different answers (Field Manual 0). A prompt that looked better on one try may just have rolled well. Run each case more than once and look at the spread.

Too few tries

Three good answers can't show a 90% success rate. They're consistent with 50%. Most real failures are rare cases you didn't think to type, and a handful of tries won't hit them.

Picking the winners

You try the questions the change was meant to fix, and you remember the good answers. Meanwhile something else broke. A fixed set run in full catches the regressions you weren't looking for.

The fix is boring and it works. Write the cases down once. Run all of them on every change. Grade them the same way each time. Field Manual 1 tells you how to write a better prompt; this manual tells you whether you did.
Part 2 · Lay out the course

Build an eval set

The eval set is the most valuable part of the whole system. Prompts and models change; a good set of cases outlives them all.

Case typeWhat it isWhere to get itShare of set
Real inputsWhat users actually send, typos and all. Your baseline.Production logs, support tickets, pilot usersMost of it
Edge casesEmpty input, very long input, other languages, ambiguous asks, questions your docs don't cover.Brainstorm with the team; past bugsA solid slice
AdversarialPrompt injection, requests to leak data or break policy, attempts to make it act out of scope.Security review, red-team sessions (Field Manual 12)A few, tagged critical
RegressionsEvery failure found in production or review, turned into a case so it can't quietly come back.Bug reports, user feedback, monitoringGrows over time

Each case needs

  • An input exactly as the system receives it, including any retrieved context or conversation history.
  • Expected behavior: a reference answer when there is one right answer, or a short rubric when many answers are fine.
  • A grader: how a pass is decided. Part 3 covers the options.
  • Tags for slicing results: topic, difficulty, source, and critical for cases that must never fail.
  • A source, so you can tell real cases from invented ones later.

How many

  • Start with 20 to 50. Enough to catch obvious breakage and to start the habit. Don't wait for a perfect set.
  • Grow toward a few hundred for decisions between close variants. Part 5 shows why: small sets only detect big differences.
  • Cover before you count. Ten cases for each important behavior beat 300 near-copies of the easy case.
  • Treat these as starting points. The calculator in Drill 3 tells you what your own set can and can't detect.

Teaching to the test

You tune the prompt case by case until the dev set passes. The score climbs; real quality doesn't.

Fix: keep a held-out set you don't look at while tuning. Run it before a release decision. If dev rises and held-out doesn't, you've overfit.

Leakage

Eval answers end up in the few-shot examples, the retrieval index, or fine-tuning data. The system has seen the answer key.

Fix: keep eval cases out of prompts, indexes and training data. Check for exact and near-duplicate overlap whenever any of them change.

A moving course

Cases get edited and added between runs, so this week's 82% and last week's 79% measure different things.

Fix: version the set in git next to the prompt. Record the set version with every run. Compare only runs on the same version, or re-run the old variant.

    Part 3 · The judges
    
    
    Kinds of graders
    
    
    A grader turns an output into pass or fail, or a score. Go down this list and stop at the first one that can decide your case. Cheaper graders are faster, free to rerun, and never disagree with themselves.
    
  
    
  
    
    
    GraderUse it forWatch out forCost
    
    
    Code checksValid JSON, required fields, a regex match, word limits, a forbidden string, a tool called with the right arguments, code that passes its tests.Checks shape, not meaning. Too strict a regex fails good answers.Free, instant
    
    
    Reference matchOne right answer: a number, a label, a date, a category. Exact match after normalizing case and spaces, or "contains".Fails correct answers phrased differently. Normalize first.Free, instant
    
    
    Human rubricTone, helpfulness, safety calls, anything subtle. Also the ground truth you calibrate every other grader against.Slow, and people disagree. Write the rubric down and measure agreement between graders.Expensive
    
    
    LLM as judgeOpen-ended answers where code can't decide, at a volume people can't keep up with.Known biases (below). It's a model too, so it needs its own eval.Cents per case
    
  
    
  
    
    
    
      
    Retrieval (Field Manual 7)
    
      
    Grade the search step on its own
    
      
      
        
    • Hit rate@k: does the right source appear in the top k results?
      • 
        
    • Recall@k: when several sources are needed, what share of them came back?
      • 
        
    • MRR (mean reciprocal rank): how high the first right source ranks, averaged.
      • 
        
    • Then grade the answer separately: correct, and supported by the cited sources. A bad answer with a good retrieval score is a prompt problem.
      • 
      
    
    
    
    
    
      
    Agents (Field Manual 2)
    
      
    Grade the outcome, then the route
    
      
      
        
    • Task success: check the end state (the file exists, the ticket is closed, the test passes). The agent saying it's done proves nothing.
      • 
        
    • Steps and tool calls: how many it took, and how many errored. Rising counts often show up before failures do.
      • 
        
    • Cost and time per task, in tokens and seconds.
      • 
        
    • Consistency: run each task several times. Report the share of tasks that succeed on every run.
      •

    Part 4 · Check the judge
    
    
    LLM judges have biases
    
    
    Research on model judges, including the MT-Bench study by Zheng and colleagues (2023), documents consistent biases. You can't remove them, but you can design around them.
    
  
    
  
    
    
    Position bias
    In a side-by-side comparison, the judge favors whichever answer comes first (or second), regardless of content.
    Fix: judge every pair twice with the order swapped. Count a win only when both orders agree; call the rest a tie. Try it in the demo below.
    
    
    Verbosity bias
    Longer, more detailed-looking answers score higher even when they add nothing or are wrong.
    Fix: tell the judge to ignore length unless the rubric mentions it, and check whether score tracks word count in your results.
    
    
    Self-preference
    A model tends to rate its own outputs, or its family's, higher.
    Fix: use a judge from a different model family than the system under test when you can, and confirm with human labels.
    
    
    Vague rubric
    "Is this a good answer? Rate 1 to 10." Scores drift and cluster in the middle.
    Fix: ask yes-or-no questions about specific points, one rubric per behavior. Ask for reasoning before the verdict. Use structured output so the verdict always parses.
    
  
    
  
    Calibrate before you trust. Have people label 50 to 100 outputs. Run the judge on the same ones. Look at where they disagree, fix the rubric, and repeat until agreement is high enough for the decision you're making. Re-check whenever you change the judge model or prompt.

    Part 5 · Read the scoreboard
    
    
    Statistics that matter
    
    
    A pass rate from a small set is an estimate with an error bar. Four habits keep you honest.
    
  
    
  
    
    
    Report an interval
    Give a 95% confidence interval with every pass rate. Use the Wilson interval: it stays sensible near 0% and 100%, where the textbook formula breaks. 16 of 20 is 80%, but the interval runs from about 58% to 92%.
    
    
    Compare on the same cases
    Run both variants on the same set and look case by case. Most cases pass or fail for both. Only the cases where they disagree carry information, and McNemar's test uses exactly those. This needs far fewer cases than comparing two separate sets.
    
    
    Sample more than once
    Run each case 3 to 5 times when temperature is above zero. Flaky cases show up, and you can score a case as passing only when every run passes. Count cases, not runs, in the interval: five runs of one case aren't five independent cases.
    
  
    
  
    How big a difference can you see? To tell 80% from 85% using two separate sets, at 95% confidence and the usual 80% power, you need roughly 900 cases per variant. To tell 70% from 90%, about 60. Paired comparisons need fewer, how many fewer depends on how often the variants agree. Small sets catch big breaks, not small gains.

    Part 7 · Standing drills
    
    
    Evals in the daily loop
    
    
    An eval run once is a report. An eval that runs on every change is a safety net. This is eval-driven development: write the failing case first, then change the system until it passes without breaking the rest.
    
  
    
  
      
    
    1. Find a failureFrom a user report, monitoring, review, or a new feature you want.
      2. 
    
    2. Write the caseAdd it to the set with a grader and tags. Run it and watch it fail.
      3. 
    
    3. Change one thingPrompt, model, retrieval, or tool. One at a time, so you know what helped.
      4. 
    
    4. Run the full setEvery case, several samples each. Read the failures as well as the score.
      5. 
    
    5. Compare, pairedAgainst the last accepted version on the same set version. Check what broke as well as what got fixed.
      6. 
    
    6. Ship, then watchMonitor production, sample real traffic for review, and send new failures back to step 1.
      7. 
  
    
  
    
    
    
      
    In CI
    
      
      
        
    • Run the cheap graders on every pull request that touches a prompt, model setting or pipeline. Keep this fast.
      • 
        
    • Fail the build on any critical case failure, or if the interval's lower bound drops below your bar.
      • 
        
    • Run the full set, with model judges, nightly or before release.
      • 
        
    • Pin the model version where your provider allows it, so a silent model update shows up as a change you chose.
      • 
      
    
    
    
    
    
      
    Over time and in production
    
      
      
        
    • Save every run: set version, system version, model, scores per case. Plot the trend per tag as well as the total.
      • 
        
    • Log inputs and outputs (within your data policy), plus user signals like thumbs down, retries and escalations.
      • 
        
    • Run code checks and a judge on a sample of live traffic. Review flagged items by hand every week.
      • 
        
    • Every confirmed failure becomes a case. The set grows toward what users actually do.

      Pocket checklist
      
    
      Before you trust a score
      
    
        
      
      • The set mixes real inputs, edge cases and adversarial cases, and every case has a source.
        • 
      
      • The set is versioned, and runs record the set version, system version and model.
        • 
      
      • A held-out set exists, and nobody tuned against it.
        • 
      
      • Eval cases appear nowhere in prompts, retrieval indexes or training data.
        • 
      
      • Code graders handle everything they can; model judges were checked against human labels.
        • 
      
      • Pairwise judging runs in both orders.
        • 
      
      • Every pass rate comes with an interval, and variants are compared on the same cases.
        • 
      
      • Critical cases block release on any failure.
        • 
    
      
  
      

      


      
  
      
    
      Appendix · Pocket card
      
    
      Cheat sheet
      
  
      
  
      CASE     input · expected (reference or rubric) · grader · tags · source
SET      real inputs + edge cases + adversarial + past failures
         dev set for tuning, held-out set for decisions, versioned in git

GRADERS  cheapest that can decide, in this order:
  1. code: JSON valid, regex, length, forbidden strings, tool args
  2. reference: exact or contains, after normalizing
  3. LLM judge: yes/no rubric points, reasoning first, structured output,
     both orders for pairs, different model family, calibrated on humans
  4. human review: ground truth and the subtle calls

RETRIEVAL  hit rate@k, recall@k, MRR, then answer quality separately
AGENTS     task success (check end state), steps, tool errors, cost, time

STATS
  Wilson 95% interval on every pass rate
  20 cases: 16/20 = 80%, interval about 58% to 92%
  80% vs 85% with separate sets: about 900 cases each
  same cases for both variants -> McNemar on the disagreements
  3-5 samples per case; count cases, not samples

LOOP     failure -> case -> one change -> full run -> paired compare -> ship -> monitor
