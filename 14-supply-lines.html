Every route needs a fallback

Supply Lines

A prototype that works on your laptop is one trip down a quiet road. Production is a supply line that runs every day, in bad weather, with the bill arriving monthly. Running an LLM feature in production means choosing the right model for each route, paying only for the tokens you need, surviving outages, and knowing within minutes when a route has gone bad.

Who it's for

Engineers and platform teams taking an LLM feature from prototype to production.

Time

About 90 minutes, a third hands-on.

Bring

Python 3.10+, Ollama with llama3.2 pulled (Field Manual 4), and pip install openai pydantic.

  • Measure before you shrink.

    Find what the strongest model can do on your eval set, then step down to the cheapest model that still clears the bar.

  • Output tokens and retries set the bill.

    Output costs more and takes longer than input. Badly timed retries multiply both.

  • Treat prompts and models like code.

    Version them, test them in CI, roll them out gradually, and keep a rollback one switch away.

Part 1 · Choose the route

Pick a model on evidence

Every model is a trade between what it can do, what it costs, how fast it answers, how much it can read, and where your data goes. Write down which of these you can't compromise on before you compare anything.

Find the ceiling, then step down

  1. Build the eval set firstReal inputs with known good answers or a grading rule. Without it, every later step is guesswork.
  2. Start with the strongest modelIt shows the ceiling. If it can't do the task, a smaller one won't either, so fix the task or the prompt.
  3. Tune the prompt on the strong modelGet the instructions, examples and output format right while the model is forgiving.
  4. Run smaller models on the same setSame prompt, same cases. Note which cases each one fails as well as its score.
  5. Pick the cheapest that clears the barInclude latency and cost per request in the decision, at your real token counts.
  6. Consider a cascadeSend most traffic to the small model and escalate the hard cases to the big one.

Cascades and routing

A router picks a model per request. Route on cheap signals you have before calling: task type, input length, customer tier. A cascade calls the small model first and escalates when its answer fails a check: schema validation, a confidence score you've tested, or a grader. Every escalation pays for both calls and waits for both, so a cascade only saves money when most requests stay on the small model. The calculator below shows the break-even.

Self-hosted or API

API: no hardware, the strongest models, elastic capacity. You pay per token, accept the provider's rate limits and data terms, and models retire on their schedule.

Self-hosted (Ollama for prototypes, a serving engine like vLLM for throughput): data stays on your hardware and you control versions. You pay for GPUs whether busy or idle, and you own scaling, patching and uptime. It usually wins on steady high volume or strict data rules.

Part 2 · Where the time and money go

The mechanics of cost and speed

Two short formulas explain most production bills and most slow responses.

cost per request = (uncached_in × Pin + cached_in × Pcached + out × Pout) ÷ 1,000,000
total time ≈ time to first token + output tokens ÷ output speed

Input vs output

Input tokens are read in parallel. Output tokens are generated one at a time, and providers usually price them several times higher. A request that writes a long answer is slow and expensive however short the question.

First token vs last

Time to first token (TTFT) covers queueing and reading the prompt, so it grows with input length. After that, total time grows with every output token. Track both.

Streaming

Streaming sends tokens as they're generated. It doesn't make the answer finish sooner, but the reader starts reading at TTFT. Use it for anything a person watches. Batch jobs don't need it.

Prompt caching

Providers can reuse the work done on a prompt prefix they've seen recently (the KV cache from Field Manual 8). Cached input is billed lower and read faster. The cache matches from the first token, so put stable content first: system prompt, tool definitions, reference documents. Put the user's message, dates and IDs last.

Batch offline work

Nightly summaries, backfills and evaluations don't need an answer in two seconds. Many providers offer a batch API with a longer turnaround, often at a discount, and it keeps bulk jobs from eating your interactive rate limit.

Cap and trim output

Set a max token limit on every call so a runaway answer can't cost a fortune. Ask for the format you need: a JSON object instead of an essay, three bullets instead of "explain". Check the finish reason, since a limit hit means a cut-off answer.

Part 6 · Change orders

Ship prompt and model changes safely

A one-word prompt edit or a new model version can change thousands of answers at once, and nothing crashes to tell you. Route every change through the same gate.

  1. Version itPrompts live in the repo with the model ID and parameters they were tested with. Every log line carries the version.
  2. Eval in CIRun the eval set (Field Manual 11) on every prompt or model change. Block the merge if the score drops below the bar.
  3. CanarySend a small share of traffic to the new version, or run it in shadow and compare without showing users.
  4. CompareQuality signals, cost per request, p95 latency, error and validation-failure rates, old vs new.
  5. RampWiden the rollout in steps while the numbers hold.
  6. Keep rollback readyThe old version stays deployable behind a flag. Rolling back is a config change, not a code change.
Pin model versions. An alias like "latest" can move to a new model under you. Where your provider offers dated or versioned model IDs, use them, and watch its deprecation notices so a retirement date never surprises you. With Ollama, pin a specific tag and record the ID that ollama list shows. Re-run your evals before each migration.
Part 7 · Perimeter

Safety in production

A public LLM endpoint is a resource others will try to use for free, or turn against you. Field Manual 12 covers attacks like prompt injection in depth. These are the operational basics.

Per-user rate limitsLimit requests and tokens per user and per key. One script shouldn't use your whole quota.
Spend capsSet budget alerts and hard caps with your provider and in your own code.
Abuse monitoringWatch for unusual volume, long inputs, repeated jailbreak patterns and off-topic use.
PII handlingSend only the data the task needs. Redact before logging. Know your provider's retention terms.
Untrusted outputEscape model output before rendering it, and validate it before it reaches a database or a shell.
Least-privilege toolsAn agent's tools get only the permissions the task needs. Risky actions need a human gate.
Prompt injectionRetrieved documents and web pages can carry instructions. Treat them as data (Field Manual 12).
Kill switchA flag that turns the feature off or to a safe fallback in seconds, without a deploy.
