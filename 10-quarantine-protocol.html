Quarantine Protocol

Vibe coding means describing what you want, letting AI write the code, and judging it by whether it seems to work rather than by reading it. It's a great way to build a prototype in an afternoon. It's also how working code ships with an exposed password or a hole anyone can walk through. This manual is the protocol for the second part: keep the speed, quarantine the risk.

Who it's for

Anyone building software with AI, engineers and non-engineers alike.

Time

About 60 minutes.

Bring

Something you've built with AI, or want to. No coding experience required for Parts 1 to 3.

Part 4 · Safer requests

Ask for safer code up front

The same tool writes much safer code when you ask for it. These additions cost one sentence each.

Vibe
Make a page where people can look up their order status.
Protocol
Make a page where signed-in customers can look up their own orders only. Use parameterized queries. Read the database password from an environment variable. List any security risks you see when you're done.
Vibe
It's broken, fix it.
Protocol
This error appears when I submit the form: [paste]. Explain the cause before changing anything. Fix the cause, don't hide the error, and add a test that would have caught it.
Vibe
Add charts.
Protocol
Add a bar chart of weekly totals. Use the charting library already in the project; don't add new dependencies. Keep the change small and tell me which files you touched.
Vibe
Looks good, ship it.
Protocol
In a fresh session: review this diff for security problems, exposed secrets, missing input validation and unhandled errors. Report only real issues, with line numbers.
Part 5 · The working loop

Small, saved, checked

Vibe coding goes wrong in big leaps: one prompt that rewrites half the project, then ten rounds of "still broken." Work in small loops you can undo.

  1. Save a checkpointCommit to git (or copy the folder) before every AI change, so any change can be undone.
  2. Ask for one changeOne feature or fix per request. Name the files. Say what not to touch.
  3. Run itTry the happy path and one weird input: empty, huge, or wrong type.
  4. Read or explain the diffIf you can't read it, ask the AI to explain each change in plain language. You own every line you keep.
  5. Run the testsAsk for tests with each change and keep them. They're how you'll know the next change didn't break this one.
  6. Commit, or roll backTwo failed fixes in a row? Roll back to the checkpoint and ask again with what you learned.
Part 6 · Signs of infection

Red flags in AI-written code

Stop and get a closer look, or a second pair of eyes, when you see any of these.

You can't explain itCode that works but you don't know why is code you can't safely change.
Errors swallowedexcept: pass, empty catch blocks, or "ignore errors" flags.
Security turned offverify=False, disabled CORS checks, debug mode in production, permissions set to everyone.
Secrets in the codeAnything that looks like a key, token or password in a file.
Unknown packagesA dependency you've never heard of. AI tools sometimes invent package names, and attackers register them.
Tests removed or skippedCommented-out tests, or assertions loosened until they pass.
Huge diffsHundreds of changed lines for a small request.
The fix loopThe third "try again" in a row. The approach is wrong, not the details.
