Quartermasters and radio operators

Outpost Protocols

A one-shot prompt asks the model to get everything right in a single roll of the dice. An agentic solution breaks the job into steps, gives each step tools to look up facts instead of guessing, and checks the work before anything leaves the gate. Each step is still a prompt. The protocol around the steps is what keeps people alive.

Drill 1

Why steps alone won't save you

Splitting a job into narrow steps makes each step easier, so each succeeds more often. But success multiplies across steps: five steps at 92% each is only 66% end to end. What changes the picture is a check after each step that catches failures, then retries or calls for help. Move the sliders.

A simplified model: steps are independent, a caught failure triggers a retry, and a step that fails every retry goes to a person and stops the run. Real numbers come from testing your own steps.

The math, for engineers

For one step with success rate p, check catch rate c and r retries, let q = (1−p)·c be the chance an attempt fails and is caught. The step ends correct with probability p·(1 + q + … + q^r), ends escalated with probability q^(r+1), and passes a silent error otherwise.

Across n independent steps, the run is fully correct with probability P_correct^n. Watch the red segment: errors that pass every check. Checks don't only raise accuracy; they turn silent failures into visible ones, which is what lets you trust the outputs you do get.

Real steps aren't independent. A wrong stock count early on poisons everything after it, which argues for putting the strongest checks on the early steps that pull facts.

Anatomy

Six decisions turn a prompt into a protocol

Whatever pattern you choose, you answer the same six questions. A one-shot prompt answers all of them with "the model will figure it out." Writing them down is most of the work.

What does done look like?

Outcome

A testable description of the result. If you can't check it, no agent can aim at it.

What must be counted, not guessed?

Tools

Every fact the model would otherwise invent becomes a lookup: the stockpile ledger, the roster, the map.

Where are the natural seams?

Steps

Split where the kind of thinking changes: sort, gather, decide, write. Each step gets its own focused prompt.

How do I know a step worked?

Checks

Code when possible (counts add up, the outpost exists), a second model pass when judgment is needed.

When does it stop?

Stop rules

A success condition, a budget of steps or time, and what to do when the budget runs out.

What needs a person?

Gates

Anything that can't be undone (medicine handed out, a vehicle sent) gets a sign-off until the protocol earns trust.

Tools are prompts too

Brief your tools like a new recruit

The model picks tools by reading their names and descriptions. A vague description puts probability on the wrong tool or the wrong arguments. Write it the way you'd brief a capable new recruit, and make error messages say what to do next.

Before
name: lookup
description: Looks up data.
params:
  q: string

error: "400 Bad Request"
After
name: check_stockpile
description: Count of one item in the main
  stockpile and each outpost cache. Use
  before approving any supply request.
  Returns count, location, and how much
  is already promised to other outposts.
params:
  item: string, a stockpile item name
    like "amoxicillin" or "water tablets".

error: "No item called 'antibiotics'. Use
  a specific name, such as 'amoxicillin'.
  Call list_stockpile to see every item."
More on tool design

Prefer a few tools that each match a real task over many thin wrappers around a database. "Find outposts within a day's walk that have spare fuel" is easier for a model to use correctly than three lookups it has to chain itself.

Return what the next step needs, in a form the model reads easily: names instead of opaque IDs where possible, and short results with a way to page for more, so tool output doesn't flood the context.

Design arguments so mistakes are hard to make: fixed lists instead of free text, absolute quantities instead of "some," and an explicit dry_run flag on anything that changes the ledger.

Known threats

How protocols fail

It never stops

Like a walker, it just keeps going: searching, retrying, "improving" long past the point of value.

Fix: give it a clear success condition and a hard budget on steps, time or cost. Say in the prompt what to do when the budget runs out: report what it has and what's missing.

One bite spreads

A wrong stock count in step 2 makes every later step confidently wrong.

Fix: put the strictest checks on fact-gathering steps. Make later steps cite the numbers they used so a check can trace them back.

The pack gets too heavy

Long tool outputs and history crowd out the instructions; quality drops late in the run.

Fix: return compact tool results, summarize finished work into notes, and send subtasks to sub-agents that report back a short result.

Silent radio

A tool error comes back empty and gets read as "outpost has no stock."

Fix: make tools tell "nothing found" apart from "something broke," and tell the model to stop and report when a tool fails twice.

The guard waves everyone through

A model grading its own work in the same context tends to approve it.

Fix: check with code where you can. For judgment calls, use a separate prompt that sees only the output and the criteria, not the reasoning behind it.

A fortress for a lemonade stand

A five-agent system for a job one good prompt with the right documents would handle.

Fix: measure the one-shot first. Add a step only when you can name the failure it fixes.
