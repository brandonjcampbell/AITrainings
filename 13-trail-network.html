Know who supplies whom

Trail Network

A vector index finds passages that sound like your question. It can't walk from one outpost to the next. A knowledge graph stores camps, outposts and the trails between them as typed, explicit connections. With a graph behind it, a model can answer questions that take more than one hop and name the report behind every fact.

Who it's for

Engineers and data architects putting LLMs on top of connected data.

Time

About 90 minutes, half hands-on.

Bring

Python 3.10+, Ollama with llama3.2 and nomic-embed-text (Field Manual 4), and Docker for Neo4j.

  • Graphs answer relationship questions.

    Who supplies whom, what is two hops away, what is cut off. Similarity search can't follow a chain.

  • The model drafts, the schema decides.

    Let the LLM extract triples and write queries. Validate both against the ontology before anything touches the graph.

  • Keep the receipts.

    Every relationship carries the ids of the reports that stated it. No source, no fact.

Part 1 · Read the map

What a knowledge graph holds

A knowledge graph is data stored as things and the typed connections between them, plus a schema that says what those types mean. Select a part.

Property graph

Neo4j and Cypher

Nodes and relationships both carry properties. Queries draw the pattern you want as ASCII art. Cypher is the main language; the ISO GQL standard (2024) grew from the same ideas.

(:Camp {key:'camp-harbor'})
  -[:SUPPLIES {sources:['r06']}]->
(:Outpost {key:'outpost-6'})

MATCH (c:Camp)-[:SUPPLIES]->(o:Outpost)
RETURN c.name, o.name

Schema is optional in the database. Uniqueness constraints exist in every edition; Enterprise adds existence and type constraints. Most of the ontology lives in your loading code.

RDF

Triples, SPARQL and OWL

Everything is a subject, predicate, object triple, named with global IRIs, so data from different sources merges cleanly. OWL describes classes and properties. SPARQL queries with property paths.

tn:harbor a tn:Camp ; tn:supplies tn:op6 .

SELECT ?site WHERE {
  tn:harbor (tn:connectsTo|^tn:connectsTo)
           /(tn:connectsTo|^tn:connectsTo)? ?site .
}

Facts about a fact (trail status, sources) need reification, named graphs or RDF 1.2 triple terms. OWL domain and range are inference rules under an open world: a wrong subject gets a new inferred type, not an error. Use SHACL to validate.

Stay with tables for flat records and arithmetic, and with vector search for "find the passage about X." Graphs earn their keep when the relationships are the question.

Part 2 · Where the archive runs out

    
What vector RAG can't do alone

    
Field Manual 7's archive run works when one or two passages hold the answer. These question shapes break it, however good the embeddings are.

  

  

    
Multi-hop
The answer needs facts from several reports that share no words with the question. "Two hops of antibiotics" retrieves the antibiotics report and nothing about the trails.
Graph: the hops are stored. A traversal follows them and returns every report on the path.

    
Global questions
"What are the main supply problems this month?" No single chunk is about that. Top k gives a few anecdotes.
Graph: aggregate in Cypher, or summarize communities of related entities ahead of time (GraphRAG).

    
Exhaustive and negative
"Every outpost cut off from Ridge." "Who has no medic?" Retrieval returns what exists, never what's missing, and k caps the list.
Graph: NOT EXISTS { } over the whole graph gives a complete answer.

    
Direction and type
"Harbor supplies OP-6" and "OP-6 supplies Harbor" embed almost the same. So do "reports to" and "is reported by."
Graph: direction and type are part of the data, not a guess from wording.

    
Stale facts
The archive keeps the old "trail open" report next to the new "washed out" one, and both rank.
Graph: one relationship, updated in place, with its sources and a timestamp.

    Part 5 · Keep the map true
    
    
    Quality is a pipeline
    
    
    An LLM-built graph inherits every extraction mistake, permanently and with a confident shape. Build these checks in from the first load.
    
  
    
  
    
    
    Extraction errors
    Negations, plans and rumors stored as facts; cargo confused with sender. Require an evidence quote that must appear verbatim in the chunk, use temperature 0, and spot-check a sample by hand every load.
    
    
    Duplicate entities
    "Outpost 3", "OP-3", "the third outpost." Resolve to canonical keys before MERGE, keep a reviewed alias table, and send unresolvable mentions to a person. Embedding similarity can suggest merges; a person or a rule approves them.
    
    
    Schema drift
    Free-text extraction invents types: SEEN_NEAR, SUPPLY, supplies. Constrain output to a closed list, reject anything else at the loader, and audit with db.relationshipTypes(). Change the ontology on purpose, with a version.
    
    
    Provenance
    Store source chunk ids on every relationship, append-only. You can then cite, audit, retract everything from a bad report, and count how many reports back a fact.
    
    
    Time
    Trails open and close. Keep updated_at and the report date. When history matters, model changes as events with their own nodes instead of overwriting.
    
    
    Evaluation
    Score extraction precision and recall against hand-labeled reports. Score text-to-Cypher by comparing result rows, not query text. Score answers end to end on a fixed question set (Field Manual 11).

      Pocket checklist
      
    
      Before the graph goes live
      
    
        
      
      • The ontology is written down, versioned, and enforced in code: labels, relationship types, domain and range.
        • 
      
      • Extraction uses structured output with a closed list of types, and rejected triples are logged.
        • 
      
      • Every node has a canonical key with a uniqueness constraint, and every load uses MERGE on it.
        • 
      
      • Every relationship carries the ids of the chunks that stated it.
        • 
      
      • Generated Cypher runs as a read-only user, with a plan-type check, a timeout and a row limit.
        • 
      
      • I have a test set of questions with expected rows, and I rerun it after any schema or prompt change.
        • 
      
      • Audit queries for duplicates, unknown types and single-source facts run on a schedule.

      Appendix · Pocket card
      
    
      Cheat sheet
      
  
      
  
      BUILD   chunk → extract (schema, closed types) → validate → resolve keys → MERGE with sources
READ    text-to-Cypher (schema + examples, read-only)  or  vector entry → traverse → context

Cypher patterns
  MATCH (a)-[:T]->(b)                    one hop, directed
  MATCH (a)-[:T]-(b)                     either direction
  MATCH (a)-[:T]-{1,2}(b)                1 to 2 hops
  MATCH (a)-[:T]->+(b)                   one or more hops
  MATCH (a)-[t:T WHERE t.status='open']-+(b)   filter during traversal
  MATCH p = SHORTEST 1 (a)-[:T]-+(b)     shortest path
  WHERE NOT EXISTS { (a)-[:T]->() }      absence
  COUNT { (a)-[:T]-() }                  degree
  MERGE (n:Entity {key: $key})           idempotent load on a unique key

Python driver (neo4j)
  driver = GraphDatabase.driver(uri, auth=(user, pw))
  records, summary, keys = driver.execute_query(q, name=..., database_="neo4j", routing_="r")
  session.execute_read(fn, ...)   tx.run(q).consume().query_type == "r"

Text-to-Cypher guard rails, outermost first
  1. a database user with read-only privileges
  2. EXPLAIN plan type must be "r"
  3. keyword tripwire, single statement only
  4. timeout and row limit
  5. schema + few-shot examples in the prompt, one retry with the error

Measure
  extraction   precision / recall of triples vs hand labels
  resolution   duplicate rate (audit query)
  text2cypher  result rows match expected rows
  answers      correct and traceable to sources
